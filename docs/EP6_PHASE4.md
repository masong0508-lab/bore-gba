
# Phase 4, step a: a realm can be played (kingplay.h)

Nothing in this step draws a map or a giant yet. It wires the realm into the game, end to end, with a plain status screen to watch it on. KINGDOM MODE > a realm > PLAY THIS KINGDOM.

- `source/kingplay.h`: `kpOpen` (stgClaim, lay the realm out in hhPool, load, start the simulation), `kpSave` (the realm saves as a fresh copy and goes on running; its slot MOVES), `kpSettle` (a new realm gets a standing storehouse, two hut sites and 6 road cells on a cleared 8 x 8 patch in the middle [ASSUMED]) and `kpRun` (the status screen: day, Nubbins, goods; UP/DOWN speed x1, x4, x16; B or START opens SAVE AND LEAVE / SAVE AND KEEP PLAYING / LEAVE WITHOUT SAVING / KEEP PLAYING). A save that fails never leaves the realm.
- A FINDING: the worst realm the simulation allows in the 128 x 128 tier (40 buildings, 512 road cells, thousands of felled trees) saves as 6.5 to 6.7 KB, but the pool has only 6,048 bytes spare there. So `kingmem.h` now puts the simulation LAST and gives two scratch areas that run to the end of the pool: `lscr` to load (the whole simulation area, not started yet) and `sscr` to save (from `KSim.dist`, which is only a cache after `ksPrepSave`, 12,192 bytes in the kingdom tier). `kingsim.h` moves `dist` and `queue` to the end of `KSim` for this. No other change to the simulation; its tests still pass.
- The realm after a save lives exactly as one that was prepared for a save but encoded elsewhere (tested over 20 days).
- Still true: the save format allows 4 slots (8,156 payload bytes). A realm with far more felled trees than the test's 3.9 thousand edits could still be refused with a full "too big" error; the sim's reach (40 buildings x 14 x 14 cells = 7,840) bounds it, and a checkerboard of all of them is not something play produces. To watch, not to fix yet.
- Not compiled for the ARM. New to the ARM build: `memset` (the king files are the only code that calls it; devkitARM's newlib has it) and `_Alignof`/`uintptr_t` (stdint.h is already included). main.c gets four `#include` lines.
- Tests: `sh tools/test_kingplay.sh` (found a realm, open it in a pool of hhPool's size, settle, run 30 days, save, reopen identical, the worst realm, mid-life save, a bad slot) on the real flash code; `test_kingmem.sh` updated for the new order.

# Phase 4, step b: the map (kingview.h, Plan B)

PLAY THIS KINGDOM now opens on the realm drawn with the GBA's hardware tile background (mode 0). D-pad scrolls (3 pixels a frame), A switches to the status screen and back, L and R change the speed, B or START opens the menu (the menu runs in mode 3: the map is switched off for it and loaded again after).

- `source/kingview.h` is pure C (its only hardware is the macro `KV_PUT`). One cell is one 8 x 8 tile. A 32 x 32 screenblock is a ring (world tile x,y at x&31, y&31) and the scroll registers show the right part of it. Crossing a tile edge writes only the newly exposed column or row; one row of the window is also refreshed every frame, so a felled tree, a road or a finished building shows within 21 frames.
- 16 tiles made in code (PLACEHOLDER art, Phase 6): 7 terrains and deep water off the map, a building's four quarters, the same four as a building site. Palette banks 1 to 7 recolour the roof by building type; bank 0 is the land.
- `tools/test_kingview.sh`: 20,000 random camera moves in each of the three sizes (up to 9 pixels a frame, jumps, corners, edges); after EVERY move all 31 x 21 tiles the hardware would show equal the world's tiles. Edits made while shown catch up in 21 frames. A normal move writes at most 104 tiles (9 pixels can cross two tile edges); at the game's 3 pixels a frame, at most 52.
- Hardware, NOT tested (no cart, no emulator, no ARM build): DISPCNT 0x0100 (mode 0, BG0 only), BG0CNT 0x0800 (charblock 0, screenblock 8), tiles at 0x06000000 (512 bytes), map at 0x06004000, BG palette 0x05000000 (128 bytes). All of it lies in the bitmap's VRAM, below the household's sprites (0x06014000, never touched) and the OBJ palette (0x05000200). Leaving mode 0 restores DISPCNT 0x0403 and repaints the bitmap from fb with dmaRows. If the first run on a cart shows garbage after leaving the map, that restore is the first place to look.
- Frame cost is still a model: the Phase 0 figure for scrolling was about 1% of a frame; the extra here is the row refresh (31 tile lookups a frame, a building search only for cells that have a building).
- Not here yet: the giant (the camera is the D-pad for now), building by hand, text over the map (the status screen is the A key).

# Phase 4, step c: the first real ARM build failed; two causes fixed (and a guard)

The GitHub Actions build of both 4a (d98c459) and 4b (0c12603) failed at `make` (`main.c`), the first time the realm code met the ARM compiler. The PC tests could not see either cause, because they compile the king files alone, without main.c's macros.

1. **`#define W 6` (main.c line 43, the creator's build space) clashed with the simulation's carrier array `KSim.W`.** Every `S->W[w]` became `S->6[w]`; the "too few arguments to ksDrop" errors were a knock-on. The member is now `wk` (kingsim.h, kinglog.h, test_kingsim.c). Same class of bug as step 3f. main.c also defines `D` (4) and `H` (8): do not use single capital letters as names in king files.
2. **`memset` and `size_t` were undeclared** (main.c includes only stdint.h; 4a's note said newlib "has" memset, but nothing declared it). The king files now call `__builtin_memset` (main.c already uses `__builtin_memmove` the same way) and cast with `(unsigned)` instead of `size_t`. The call links against the same libc as that memmove.
3. **Guard:** `sh tools/test_kingparse.sh` parses all of main.c with the host compiler and fails on any error other than the 14 ARM-only `target("arm")` ones (baseline), and on any implicit-declaration or redefinition warning in a king file. Run it with every step from now on; it reproduces both failures on the unfixed 4b tree.
- Still not verified: the ARM link, `make size` (IWRAM and EWRAM budgets), `make creator`, and everything in 4a/4b that touches hardware. The next green CI run is the first real check; after it, the cart or emulator look at the mode 0 map.

# Phase 4, step d: building by hand (kinghand.h)

On the map, the cell under the MIDDLE of the screen is the cursor (the D-pad scrolls the map under it), and it blinks (palette bank 15, the land's palette brightened). A does the current mode's action on that cell; L and R change the mode: ROAD (lay or lift), HUT, HOUSE, WOODCUTTER, QUARRY, SAWMILL, MASON, STOREHOUSE (each puts a building SITE down, top left corner on the cursor; workers carry its goods and raise it), DEMOLISH (any cell of a building's 2 x 2). A success shows on the map; a refusal (CANNOT BUILD HERE, NO ROOM FOR MORE, NOTHING HERE) and every mode change are said in a toast. KEYS CHANGED: B now switches between the map and the status screen, SELECT cycles the speed, START opens the menu (L and R are the modes now).
- `source/kinghand.h` is pure C. Its prefix is `kh` and its modes `KHM_`, errors `KHR_` (a first try with `kb` clashed with kingdom.h's byte buffer `kbInit`: caught by the PC test at once).
- `tools/test_kinghand.sh`: every mode on grass, water, buildings, the border and off the realm; every building type placed, seen by the view, demolished from its far corner, and the books (ksCheck) checked each time; the building cap; 20,000 random presses with the simulation running between them, books balanced and the view equal to the world after each batch (three tiers).
- `tools/test_kingparse.sh` passes with it wired in (host parse of main.c).
- NOT tested: the blink and the toast in mode 0 on a cart or emulator. The toast is drawn into the mode 3 bitmap, so each message leaves the map for its length and the map is loaded again after (the background is whatever the bitmap held before); real text over the map is still to do (a text layer or sprites, Phase 6).
- Costs are not charged yet: a site asks the stockpile for its goods through the ordinary matcher, so building too much just starves.

# Phase 4, step e: text over the map (BG1)

Replaces step 4d's toasts, which left the map. The map now has a second hardware background, BG1, in front of it, showing two lines of text over the bottom 16 pixels: line 1 (gold) the mode, the day, the Nubbins and the speed, line 2 (white) what is under the cursor (terrain, or a building with its state: SITE with goods delivered, NUBBINS n OF max for homes, WORKING or NO WORKER, STOCKPILE) or, for 1.25 seconds after A, what the press did.
- How: the two lines are drawn with the game's own `text()` into the first 16 rows of `fb` (not shown in mode 0), then `khStrip` (pure C, kinghand.h) turns those 240 x 16 pixels into 60 tiles of 4 bits a pixel: colour 0 stays see-through, the shadow colour becomes 2, anything else 1. Tiles 16 to 75 of charblock 0 are the text, tile 76 is a see-through tile that fills the rest of BG1's map (screenblock 9, 0x06004800); palette bank 14 holds white and a dark shadow. DISPCNT 0x0300 (BG0 and BG1), BG0CNT 0x0801 (priority 1), BG1CNT 0x0900 (priority 0). The text is rebuilt only when it changes (the cursor moved, a press, the speed, every 64 frames for the day).
- Tests: `tools/test_kinghand.sh` now also checks the info text on every cell of a realm including off the edge, a site, a finished store, a home with 3 Nubbins, the status line at its caps, and that `khStrip` makes exactly the pixels it is given into tiles (every pixel of a noisy strip). No info line is longer than 21 characters.
- NOT tested on a cart or emulator: BG1 itself (priorities, the see-through tile, the palette bank). If the map shows junk instead of text, check the see-through fill first; if the text is under the map, check the two priorities.
- The first 16 rows of `fb` are scratch while the map shows; the menu and the status screen repaint everything, so nothing leaks into them.

# Phase 4, step f: the build menu (with costs)

START now opens a menu whose first line is BUILD MENU (then SAVE AND LEAVE, SAVE AND KEEP PLAYING, LEAVE WITHOUT SAVING, KEEP PLAYING). BUILD MENU lists the nine modes one a line, each with its cost and what the stockpile holds: `SAWMILL  4 WOOD  HAVE 12`, `MASON  3 PLANKS  HAVE 0`, `ROAD  FREE`, `DEMOLISH  GOODS COME BACK`. A picks the mode (the map comes back in it), B backs out. L and R still cycle the modes quickly.
- `khCost` (kinghand.h, pure C) writes the line; the cost is the building's `costN` of its `costG` good (a site is raised from goods the carriers bring, so this is what the site will ask the stockpile for; nothing is taken when you press A, and a site with no goods simply waits). The menu is the game's own `menu()`, run in mode 3 like the other menus, so it needs no new hardware.
- Tests: every line is at most 40 characters (the longest is 27), the road and demolish wording, a sawmill and a mason with real stockpile numbers, a stockpile of 65,000 and of 70,000 (shown capped at 99,999), and that every building's line names its own good.
- Not tested on a cart: the menu itself (it is the game's existing one).

# Phase 4, step g: the walking giant (kinggiant.h)

The camera is no longer the cursor. You are a giant: the D-pad walks it, the camera follows, and A acts on the cell under its feet (the cell blinks).
- **Controls (changed):** D-pad walks; **B held runs**; A acts in the current mode; L and R change the mode; **SELECT** shows the status screen (B also leaves it); **START** is the menu, which now has a **SPEED** line (it moved from SELECT, because B and SELECT were taken). The new first mode is **HAND**: A gathers a tree, a rock or a crystal on the giant's cell (it becomes grass and the goods go to the stockpile through `ksGift`, so the books balance). Everything else (roads, sites, demolish) works as in 4d, at the giant's feet.
- **Stats [ASSUMED, tune in kinghand.h]:** stride (pixels a frame) A 3, B 4, C 2, D 3, own Bore 3; run = stride + half (3 to 5, 4 to 6, 2 to 3; always under 8, so a frame never skips a cell); goods per hand-gathered resource 2 (C, the lifter, 3). A woodcutter gives 1 and takes 90 frames. The "build" stat of the roadmap has no effect yet.
- **Walking:** each axis on its own, so it slides along water and the border. It may not stand on water or in the 1 cell border; it walks over buildings (it is a giant). It starts on the nearest dry cell to the middle of the land. Its position is NOT saved: PLAY always starts it in the middle.
- **Camera:** centred on the giant and clamped to the land, so near an edge the giant leaves the middle of the screen (and every cell of the land but the border can be reached).
- **Sprite:** one hardware sprite, OAM entry 0: 16 x 16, 4 bits a pixel, 2 walk frames (tiles 0 to 7 at 0x06010000, which is where OBJ tiles start in mode 0), OBJ palette bank 0 (a shirt colour for each giant), priority 1 (over the map, under the text layer), flipped by hardware to face left. Placeholder art (Phase 6). Switched off (attribute 0 = 0x200) when it is off the screen, and by `objHideAll()` on entering and leaving the map. DISPCNT is now 0x1340 (mode 0, BG0, BG1, sprites, 1D tiles). The tiles overwrite the bottom of the mode 3 bitmap in VRAM (0x06010000 to 0x060100FF), which `kvHwLeave` repaints from `fb` as it did for the BG tiles.
- **Tests:** `tools/test_kinggiant.sh` (40,000 random frames in each tier: never on water or outside the border, never 8 pixels in a frame, always on the screen; water, roads, buildings, the border, all-water and dry-island spawn; the camera at the middle and the corners; every pixel of both frames, the outline, five palettes; the OAM words at every screen position). `tools/test_kinghand.sh` now also covers HAND (every giant, tree, rock and crystal; refusals; the stockpile ceiling; books balanced). `tools/test_kingparse.sh` passes with it wired in.
- **NOT tested (no cart, no emulator, no ARM build):** the sprite itself (if the giant is junk or invisible, check that OBJ tiles are at 0x06010000 in mode 0 and DISPCNT has bit 6 and bit 12; if it is under the map, check the priorities: BG0 is 1, the sprite 1, BG1 0), the OAM write timing (written right after `vsync`), the hand-gather feel and the stat values.
- Still to do in Phase 4: pick up and put down, the overview, a stockpile display beyond the status screen, a refusal when a site cannot be afforded.
